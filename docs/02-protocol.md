# 通信协议 v1（实现契约）

> 本文件是**实现契约**，不是构想。`firmware/proto/` 与 `tests/test_proto.c` 是它的可执行形式；
> 两者冲突时以测试为准，并立刻回来改这里。
>
> 沿用原 `protocol.md` 的帧格式（已验证 8/8 样例帧 CRC 正确），本文件补齐原文档缺失的**无效值语义、丢包统计口径、接收端契约、测量方法**。

---

## 1. 设计约束（先看约束，再定字段）

| 约束 | 来源 | 影响 |
|---|---|---|
| BLE 默认 MTU 23 → 有效载荷 20 字节 | BLE 4.2 | 单帧 ≤20 字节，避免链路层分片 |
| 状态更新 5Hz | 导航体验 | 每帧周期 200ms，带宽 16×5 = 80 B/s |
| DX-BT24 出厂 9600 8N1 | 模块手册 | 960 B/s，占用 8%，不必改波特率 |
| 单帧传输时间 | 9600 8N1 = 10 bit/字节 | 16 字节 ≈ **16.7ms**（这个数是 50ms 超时阈值的依据） |

**结论：16 字节定长，单包可发，不分片。**

---

## 2. 帧格式

所有多字节字段**小端序**。

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 2 | `header` | — | 固定 `A5 5A` |
| 2 | 1 | `ver` | u8 | v1 = `0x01` |
| 3 | 1 | `type` | u8 | `0x01` 状态帧 / `0x02` 路线帧(V2) / `0x10` 控制帧(V2) |
| 4 | 1 | `seq` | u8 | 0～255 循环 |
| 5 | 1 | `turn` | u8 | 转向枚举，见 §3 |
| 6 | 2 | `dist_m` | u16 | 距下一动作距离，**米** |
| 8 | 1 | `speed_kmh` | u8 | 车速 |
| 9 | 1 | `flags` | u8 | 见 §4 |
| 10 | 2 | `remain_dam` | u16 | 剩余总里程，**单位 10 米**（可表 655.35km） |
| 12 | 2 | `eta_min` | u16 | 剩余时间，分钟 |
| 14 | 2 | `crc16` | u16 | CRC-16/MODBUS，覆盖偏移 0～13，低字节在前 |

固定 **16 字节**。

> **为什么混用两种单位**：`dist_m` 要精确到米（"3 米后右转"），`remain_dam` 要足够大（65535 米只有 65km，不够用）。
> 代价是同帧内两种单位并存，**字段名必须带单位后缀**（`dist_m` / `remain_dam`），否则半年后自己会写错。这是本协议唯一容易埋 bug 的地方。

## 3. 转向枚举与无效值

```c
typedef enum {
    TURN_STRAIGHT      = 0,
    TURN_LEFT          = 1,
    TURN_RIGHT         = 2,
    TURN_SLIGHT_LEFT   = 3,   /* 左前方 / 靠左 */
    TURN_SLIGHT_RIGHT  = 4,   /* 右前方 / 靠右 */
    TURN_UTURN         = 5,
    TURN_ARRIVE        = 6,
    TURN_UNKNOWN       = 7    /* 保留：无效/未知，UI 显示直行 + 灰色 */
} turn_t;
```

**无效值约定**（原文档缺失，必须补，否则 UI 会显示"0 米右转"这种假数据）：

| 字段 | 无效值 | UI 行为 |
|---|---|---|
| `turn` | `7` 或 >7 | 显示直行图标，置灰 |
| `dist_m` | `0xFFFF` | 显示 `--`，不显示 0 |
| `remain_dam` | `0xFFFF` | 显示 `--` |
| `eta_min` | `0xFFFF` | 显示 `--` |

> 这条约定的价值：GPS 漂移时手机端确实会算不出距离，**显示 `--` 而不是 `0`** 是"产品可用性"和"写代码凑数"的分界线。

## 4. 标志位

| bit | 含义 | UI 行为 |
|---|---|---|
| 0 | 偏航（已偏离路线） | 顶部红色横幅"已偏航" |
| 1 | 定位有效（GPS fix） | 无效时整体置灰 |
| 2 | 静音（用户按了静音键） | 蜂鸣器不响，状态页显示静音图标 |
| 3～7 | 保留，必须填 0 | 收到非 0 忽略即可（不做版本判定） |

## 5. CRC-16/MODBUS

多项式 `0x8005`（反射 `0xA001`），初值 `0xFFFF`，不异或输出，覆盖 0～13 共 14 字节。
标准向量：`"123456789"` → `0x4B37`（见 `tests/test_proto.c` 第一项）。

**为什么 CRC 要覆盖帧头**：帧头是重同步的唯一依据，如果帧头本身错了而 CRC 没覆盖，会把噪声当帧头反复误锁。覆盖 14 字节的成本是零。

## 6. 接收端契约

`proto_feed(p, byte, now_ms, &out)` 的行为表：

| 输入情形 | 返回 | 说明 |
|---|---|---|
| 未收齐 | `PROTO_WAIT` | 继续喂 |
| 收齐且 CRC/ver/type 全过 | `PROTO_OK`，`out` 有效 | 上层据此刷新 UI |
| CRC 错 | `PROTO_DROP_CRC` | **只回退 1 字节**重同步，不清空缓冲 |
| `ver` 不认识 | `PROTO_DROP_VER` | 拒收；`n_drop_ver` 计数用于上报 |
| `type` 不认识 | `PROTO_DROP_TYPE` | 同上（V1 只接受 `0x01`） |
| 半帧停顿 > 50ms | `PROTO_WAIT` + `n_timeout++` | 状态机主动回 IDLE，防波特率错时永久卡死 |

**三条硬规则**（写代码前先记住，测试里都有对应用例）：

1. **CRC 失败只丢 1 字节**，不许清空缓冲区。清空会把缓冲里已有的下一个好帧一起丢掉，表现为"错一帧、连丢一串"。
2. **半帧 50ms 超时**。依据：16 字节 @9600 ≈ 16.7ms，留 3 倍裕量。
3. **UI 任务不解析字节**。`comms` 任务产出结构体，`ui` 只读结构体。

## 7. 时序、丢包与断连

| 项目 | 规则 |
|---|---|
| 正常周期 | 200ms（5Hz） |
| 断连阈值 | 连续 **3 秒**未收到 `PROTO_OK` |
| 断连动作 | 覆盖提示"信号中断"，距离/转向**置灰并冻结**，不得继续显示旧数据 |
| 恢复条件 | 连续 **2 帧** `PROTO_OK` 后解除（防抖动） |
| seq 回绕 | `255 → 0` 视为正常，不计数 |
| 统计口径 | `丢帧数 += (seq_now - seq_prev - 1) & 0xFF`；`丢包率 = 丢帧数 / (收帧数 + 丢帧数)` |
| 重传 | **不做**。5Hz 状态帧允许丢，下一帧覆盖 |

> `seq` 的定位：只用于**统计链路质量**和区分"没发 vs 没收"。面试若被问"为什么不做重传"，答"状态帧有 200ms 时效性，重传的旧数据比没有更糟"。

## 8. 版本演进

- `type=0x02` 路线帧（V2）：路线 ID + 分片号 + 折线点，需提高 MTU 或做分片重组。
- 中文道路名：单帧放不下，独立分片字段，超时丢弃整条。
- **升 `ver` 时，接收端遇到不认识的版本必须拒收并计数上报**，不许静默忽略。

## 10. 延迟测量方法（原文档的"录像逐帧看"不够）

分两段测，别混在一起：

| 段 | 含义 | 方法 |
|---|---|---|
| 协议段 | 字节进 UART → 解析出结构体 | 板子收到 `PROTO_OK` 立刻回一行 `OK <seq>\r\n`，PC 端记录发送时刻与收到时刻之差，取 100 帧均值/最大值 —— 这是 **RTT，含双向链路**，需注明 |
| 显示段 | 结构体 → 屏幕可见变化 | 手机 240fps 慢动作录像，数帧差（粗值，只用于量级判断） |
