# 设计决策记录（面试主战场）

> 每条格式：**决策 / 反方案 / 代价 / 一句话怎么讲**。
> 这里的内容不是"标准答案"，是**你自己项目里的选择**——面试时能落到具体代码和具体数字上，才有意义。
> 凡是标 `⚠` 的，是原规划里理由不成立、我重新论证过的部分。

---

## 协议层

### D1 · 16 字节定长帧，不加长度字段
- **反方案**：TLV（type-length-value）变长帧，扩展性好。
- **代价**：字段满了就是满了，V2 想传折线必须升 `ver` 换格式。
- **怎么讲**：BLE 默认有效载荷 20 字节，定长让状态机退化成"计数到 16 就校验"，不需要长度分支和越界保护；这是拿扩展性换"少一个出 bug 的地方"。

### D2 · `dist_m` 用米、`remain_dam` 用 10 米（混用单位）
- **反方案**：全部用米（65535m 不够）或全部用 10 米（"3 米后右转"显示不了）。
- **代价**：同帧两种单位，**这是本协议唯一容易埋 bug 的地方**。
- **怎么讲**：两个字段的精度需求和量程需求冲突，只能拆开；因此字段名必须带单位后缀，否则半年后自己会写错。

### D3 · CRC 失败只回退 1 字节（贪心重同步）
- **反方案**：清空缓冲区重新找帧头（实现简单）。
- **代价**：重同步时会反复误判假帧头，多花几次 CRC 计算。
- **怎么讲**：清空会把缓冲里**已经收进的下一帧开头**一起丢掉，表现为"错一帧、连丢一串"。定长 + 强校验让误锁的代价可控，所以我敢用最省的重同步策略。**这条有专门的单元测试**（坏帧紧跟好帧，必须只出 1 帧有效）。

### D4 · `seq` 不做重传
- **反方案**：超时重传 / 请求补发。
- **代价**：丢包直接体现为 UI 更新晚 200ms。
- **怎么讲**：5Hz 导航状态有 200ms 时效性，**重传的旧数据比没有更糟**。`seq` 只用于统计丢包率和区分"没发/没收"。

### D5 · CRC 覆盖帧头
- **反方案**：只校验 payload。
- **怎么讲**：帧头是重同步的唯一依据；帧头错了而 CRC 没覆盖，会把噪声当帧头反复误锁。成本为零。

## 传输与架构

### D6 · 蓝牙走 USART1，日志走 USART2（VCP）
- **反方案**：一个串口复用到死。
- **怎么讲**：USART2 已通过板载跳线接 ST-Link 虚拟串口，`printf` 是调试刚需，不能和业务数据抢；USART1 空着就给蓝牙。

### D7 · M3 用板载 VCP 灌帧，不买 USB-TTL
- **反方案**：等 USB-TTL 到货再验证协议。
- **怎么讲**：`proto_feed()` 只认字节不认串口，所以物理层可以换；先用零成本的 VCP 把协议和 UI 打通，蓝牙到货后只改"从哪个 UART 取字节"。**这是分层设计最直接的收益，不是口头说说。**

### D8 ⚠ · 3 个任务，而不是 5 个
- **反方案**（原规划）：`ble_rx` / `proto` / `ui` / `key` / `monitor` 五任务。
- **代价**：任务粒度变粗，`key` 与 `mon` 合并后需要自己管时序。
- **怎么讲**：`ble_rx` 的活其实在中断里；`proto` 是纯计算，5Hz × 16 字节的 CPU 占用可以忽略，不值得一个独立任务。真正需要拆开的只有三件事：**收字节 / 渲染 / 监控**。任务多不等于设计好，任务少且职责清楚才是。

### D9 ⚠ · RTOS 的真正理由：LVGL 渲染阻塞
- **反方案**：超循环一路到底（V1 阶段 A 就是这么做）。
- **怎么讲**：LVGL 单帧渲染 15～25ms，这期间超循环无法处理 UART；5Hz 帧间隔 200ms，虽然多数情况不会丢，但**渲染耗时抖动 + 帧到达相位**会造成偶发堆叠。用队列把"接收"和"渲染"解耦是上 RTOS 的**可验证理由**，不是"分层好看"。

### D10 · 最新值邮箱，不是消息流
- **反方案**：普通 FIFO 队列，每帧必达。
- **怎么讲**：导航状态是**状态量不是事件量**，UI 显示 3 帧前的距离没有意义；队列满时丢最旧的（或直接覆盖），保证 UI 永远看最新值。

### D11 · 喂狗条件 = 两个心跳都推进
- **反方案**：`mon` 任务自己活着就喂。
- **怎么讲**：`mon` 在跑不代表 `comms`/`ui` 没死锁，只看自己的喂狗是**假安全**。正确做法是让 `comms`/`ui` 各自递增心跳计数，`mon` 检查两个计数都比上次大才喂。

### D12 · `firmware/proto/` 不 include 任何 HAL/FreeRTOS 头
- **反方案**：直接在 `main.c` 里写解析，图省事。
- **怎么讲**：解析核心能在 PC 上用 gcc 编译，才有 `tests/` 的 96 项用例；否则每个 bug 都要烧板子看现象。这是本项目唯一"低成本高质量"的来源，也是简历上"可测试性"的证据。

## 显示

### D13 · 240×40 双缓冲 + 脏矩形
- **反方案**：全屏缓冲（240×320×2 = 150KB > 128KB RAM）。
- **代价**：需要 `flush_cb` + `lv_disp_flush_ready()`，DMA 与 UI 的切换时序要自己管。
- **怎么讲**：RAM 装不下全屏，1/8 屏双缓冲 38.4KB，配合 LVGL 的脏矩形只刷变化区域，实测单帧 ≤40ms 足够 5Hz。

### D14 ⚠ · V1 不做中文字库
- **反方案**（原规划）：`lv_font_conv` 子集化，放 Flash。
- **代价**：界面只有符号 + 数字 + 英文；中文字段（"右转"/"已偏航"）用图标替代。
- **怎么讲**：字库子集需要 Node 工具链 + 字形挑选 + Flash 占用核算，1～2 天，且不增加任何评分点；**资源受限时先砍"不影响功能正确性"的装饰**。这是范围控制的判断，不是能力不足。

## 计划与方法

### D15 ⚠ · 每个里程碑先定"退路"
- **反方案**：按理想路径排期，卡住就硬扛。
- **怎么讲**：第一次做项目最常见的死法不是技术不会，是**卡在某一环不肯降级**。M4 若 LVGL 移植超过 2 天就换自研极简绘图层，保底能演示——先交一个能跑的版本，再迭代。

### D16 ⚠ · 测试是协议的唯一真源
- **怎么讲**：改协议的正确顺序是"先改 `tests/test_proto.c` 让它红，再改实现让它绿"。文档里的样例帧会过期，测试不会。这也是我在 `02-protocol.md` 里只引用测试、不重复列举帧的原因——**两处维护必然不同步**。
