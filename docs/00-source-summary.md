### 2. `docs/protocol.md` —— 通信协议 v1

- **16 字节定长帧**，小端；字段：`header(A5 5A)` `ver` `type` `seq` `turn` `dist_m(H)` `speed_kmh` `flags` `remain_dam(H)` `eta_min(H)` `crc16(H)`。
- 约束推导链：BLE 默认 MTU 23 → 有效载荷 20 字节 → 单帧 ≤20 → 16 字节单包可发不分片；9600 8N1 = 960 B/s，需求 80 B/s 占 8%。
- `turn` 枚举 7 种（直行/左/右/左前/右前/掉头/到达）；`flags` bit0 偏航、bit1 定位有效、bit2 静音。
- CRC-16/MODBUS（0xA001 反射、初值 0xFFFF、不异或输出），标准向量 `"123456789" → 0x4B37`。
- **8 条样例帧**（覆盖面：右转/右转/左转/掉头/直行 9990m/到达/偏航/静音），带十六进制全文。
- 接收状态机 4 态 `IDLE / WAIT_LSB / RECV / CHECK`，**三条硬规则**：① CRC 失败只丢 1 字节（不许清空缓冲）；② 半帧 50ms 超时；③ UI 任务不解析字节。
- 时序：200ms 周期、3 秒断连阈值、连续 2 帧有效后恢复、seq 只统计丢包不重传、255→0 视为正常。
- V2 预留：`type=0x02` 路线帧（需 MTU 提高或分片）、中文道路名分片、版本升级拒收而非静默忽略。

### 3. `docs/wiring.md` —— 接线表（NUCLEO-F446RE）

| 外设 | 接口 | 引脚 | 关键提示 |
|---|---|---|---|
| ST7789 屏 | SPI1 | SCK=PA5、MOSI=PA7、CS=PB6、DC=PB5、RST=PB4 | VCC **3.3V**；MISO 不接；PA5 与板载 LD2 共用（灯跟着闪正常） |
| DX-BT24 | USART1 | TX=PA9、RX=PA10 | TX/RX 必须交叉；**先量模块 TXD 空闲电平**，5V 要分压 |
| 调试日志 | USART2 | PA2/PA3 | 板载跳线已接 ST-Link VCP，**勿挪用** |
| 按键 ×3 | GPIO | PA0/PA1/PA4 | 内部上拉，按下接地，20ms 消抖 |
| 蜂鸣器 | GPIO | PB10 → 1kΩ → S8050 → 蜂鸣器 | 不能直驱 |

上电顺序：只插 USB → 量 3.3V/5V → 接屏 → 最后接蓝牙；不许一次全插。

### 4. `docs/bringup.md` —— 7 阶段上电验收

阶段 0 板子验收（VCP 识别 / 型号 / 全片擦除 / 点灯 / printf / 电压 / 30min 稳定）→ 阶段 1 屏幕（三纯色 / 棋盘格 / 颜色 / 15→30MHz 测上限 / 重启 20 次）→ 阶段 2 LVGL（16bit 色深 / 240×40 双缓冲 / 中文字库子集 / 单帧耗时）→ 阶段 3 **PC 模拟数据打通（关键里程碑，8 项）**→ 阶段 4 蓝牙单机验证（AT 指令 / nRF Connect / 服务 0xFFE0 / 特征 0xFFE1、0xFFE2）→ 阶段 5 手机全链路 → 阶段 6 异常与交付（拔模块 / IWDG / 消抖 / 视频）。
末尾一张**量化指标表**：单帧刷新耗时、稳定 SPI 时钟、端到端延迟、重连恢复时间、连续运行时长、RAM/Flash 占用、丢包率——每项标了测量方法。

### 5. `tools/sim_sender.py` —— PC 端帧模拟器

`--selftest` 验 CRC 与帧长、`--demo` 打印样例帧、`--port COMx --baud 9600` 按 5Hz 发一条模拟路线（右→左→右前→掉头→到达，距离递减），Ctrl+C 即模拟断连。CRC 与组帧实现正确。

## 第二部分：我的核对结果

| 项 | 我的结论 | 依据 |
|---|---|---|
| 8 条样例帧的 CRC | **8/8 正确** | 独立实现 CRC-16/MODBUS 复算，全部匹配；标准向量 `0x4B37` 通过 |
| 帧字段自洽性 | 通过 | 长度 16、小端、`remain_dam = remain_m/10` 逐条对得上 |
| 引脚分配 | 技术上位可行 | USART1=PA9/PA10、USART2=PA2/PA3、SPI1=PA5/PA7 与 F446 数据手册一致；PB4/PB5/PB6 作普通 GPIO 无冲突 |
| 协议工程推理 | 站得住 | 定长/BLE 载荷/带宽占用/CRC 贪心重同步，都能自圆其说 |
| V1 边界 | 合理 | 砍手机 App 与地图渲染是正确的范围控制 |

## 第三部分：我推翻或修改的部分

> 这些不是"原文错了"，而是"对一个第一次独立做项目的人，代价过高或缺少工程理由"。

| # | 原文 | 我的决定 | 理由 |
|---|---|---|---|
| 1 | 5 个 FreeRTOS 任务 | **3 个任务，且推迟到 M5** | 1 周内的新手同时调 DMA、LVGL、RTOS 优先级，失败时无法归因。先用超循环把链路跑通，再换 RTOS——而且换的那一步本身就是一个好故事 |
| 2 | "分层好看所以用 RTOS" | **给出可验证的工程理由** | 真正的理由是：LVGL 单帧渲染 15～25ms，超循环下这段时间 UART 无人处理，5Hz 帧会堆叠；用队列把接收与渲染解耦才是动机。这个理由能扛住追问 |
| 3 | 中文字库子集（`lv_font_conv`） | **V1 不做中文字库** | 需要 Node 工具链 + 字形挑选 + Flash 占用核算，1～2 天，且不影响评分点。V1 用 LVGL 内置符号字体 + 自绘箭头；中文作为 M4 的可选增量 |
| 4 | 验收清单只有"应该怎样" | **每个里程碑加"退路/砍线"** | 第一次做项目最常见的死法是"卡在某一环不肯降级"。每个里程碑先想好降级方案，才敢往下走 |
| 5 | 协议核心只存在设想里 | **落成 PC 可跑的纯 C + 96 项测试** | 硬件没到之前唯一能做的正确的事；也是简历上"可测试性"的证据 |
| 6 | 没有版本管理 | **git + 单一真源测试** | 无仓库链接的项目在简历上打折；测试是协议的唯一真源，改协议先改测试 |
| 7 | 端到端延迟"双设备同框录像逐帧看" | **回显 RTT 测量 + 录像分段法** | 录像法只能测到含人眼判断的粗值。板子收到合规帧立刻回一行 `OK <seq>`，PC 端测 RTT 可得"链路+解析"延迟；录像只用于显示延迟 |
| 8 | 喂狗只看"任务还活着" | **喂狗条件 = 两个心跳都在推进** | `mon` 任务自己在跑不代表 `comms`/`ui` 没死锁，这种喂狗是假安全，面试一问就露 |
| 9 | 阶段 3 用 USB-TTL 接 USART1 | **M3 直接用板载 VCP（USART2）** | 零额外硬件、到货当天可做；`proto_feed()` 不认串口，之后切 USART1 成本≈0 |
| 10 | 未提 printf 与协议数据抢同一串口 | **工具加 `--log`** | VCP 上既要发帧又要看日志，两个软件抢同一个 COM 口是实操必踩的坑 |

## 一句话

原文档的**协议层和边界控制是可信的，可以直接继承**；**软件架构与执行计划需要按"新手单线程推进"重排**。它像一份合格的毕业设计要求，不像一份能在五周内交出可演示成果的施工图。
